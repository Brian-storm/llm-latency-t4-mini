# Analysis Notes

## What I measured

- Model: Qwen/Qwen2.5-3B-Instruct (FP16)
- Hardware: Kaggle Tesla T4 (sm75), 15GB
- Backend: HuggingFace `transformers`, manual timing loop with KV cache
- Input lengths: 64, 128, 256, 512, 1024 tokens (approximated by word count)
- Output: fixed at 64 tokens
- 10 requests per input length, 50 total
- 3 warm-up iterations before measurement

## What I found

### 1. TTFT rises with input length

From **71.2 ms** at 64 tokens to **301.1 ms** at 1024 tokens — a **4.2×**
increase. This is consistent with prefill being compute-bound: more input
tokens means more matrix-multiply work before the first output token.

Per-length medians:

| Input length | TTFT median |
|---|---|
| 64 | 71.2 ms |
| 128 | 70.7 ms |
| 256 | 71.5 ms |
| 512 | 121.9 ms |
| 1024 | 301.1 ms |

Note the flat region between 64 and 256 tokens. Prefill cost is roughly
constant up to a point, then rises sharply once the attention cost starts
to dominate. This is a real observation, not a measurement artifact — the
10 samples at each length are tightly clustered (see
`data/my_benchmark_results.csv`).

### 2. TPOT also rises with input length

From **71.6 ms** at 64 tokens to **554.0 ms** at 1024 tokens — a **7.7×**
increase. This contradicts the simple "decode is bandwidth-bound,
independent of input length" picture.

| Input length | TPOT median |
|---|---|
| 64 | 71.6 ms |
| 128 | 70.5 ms |
| 256 | 116.2 ms |
| 512 | 242.1 ms |
| 1024 | 554.0 ms |

**Likely cause**: each decode step attends over the full KV cache, whose
size grows linearly with input length. In a production engine (vLLM with
PagedAttention, optimized attention kernels) this growth is much flatter.
In a manual `transformers` loop with a naive attention implementation, it
dominates.

**This is a real effect, not a bug.** It reflects the fact that "decode
is bandwidth-bound" describes the *weight-loading* cost, not the whole
decode step. The attention component scales with context length and is
visible once the context is long enough.

### 3. p99 TTFT grows faster than p50

Long inputs widen the tail more than they shift the median. The p50/p99
bar chart (`figures/ttft_p50_p99.png`) shows this clearly. This is the
practical argument for looking at p99 rather than mean latency.

## Debugging notes

Two problems came up during setup, both documented here because they
affect reproducibility:

- **vLLM did not install cleanly on the T4.** The T4 is sm75, and vLLM's
  optimized kernels target sm80+. I also hit a pip dependency conflict in
  the Kaggle environment (numpy, fsspec, and others). I switched to a
  manual `transformers` loop with `past_key_values` to keep the setup
  transparent and under my control.

- **First forward pass was ~32× slower than steady state**
  (2274 ms vs 70 ms TTFT). Cause: CUDA kernel initialization and memory
  allocation on the first call. Fix: 3 warm-up iterations before
  measurement. Without warm-up, the first data point of every run would
  be an outlier of ~2 s, which would corrupt the median.

## Limitations

- **Single model, single GPU.** Results are not generalizable to other
  model sizes or hardware.
- **Transformers, not vLLM.** No PagedAttention, no continuous batching,
  so absolute TPOT is higher than a production serving engine would
  achieve. The *relative* trends are still valid.
- **Input length approximated.** Prompts were generated by word count,
  not tokenizer-exact token count. Actual token counts may differ by
  ~20–30%. The x-axis labels are approximate.
- **Output fixed at 64 tokens.** TPOT at longer generations may be
  slightly higher due to KV-cache growth.
- **No concurrency.** All requests were sent one at a time, so this does
  not capture batching effects or neighbor interference. The "TPOT is
  affected by neighbors' prefill" story from the reference notebook is
  *not* tested here.
- **10 samples per length.** Enough to see a trend, not enough for strict
  statistical claims. The within-length spread is small (see CSV), but
  cross-host variation is not controlled.
- **TPOT includes KV-cache attention cost.** The `transformers` loop
  recomputes attention over the full cache at every step, so TPOT grows
  with input length. A production engine would show a much flatter TPOT
  curve. The *direction* of the effect is real; the *magnitude* is
  implementation-specific.

## What I would do next

- Add a concurrency sweep (1, 2, 4, 8) to observe TPOT degradation and
  test the neighbor-prefill hypothesis.
- Compare against vLLM on a GPU where it runs cleanly (sm80+), to separate
  the "real" TPOT-vs-context effect from the "naive attention" effect.
- Use a tokenizer-exact input length instead of word-count approximation.
- Add a 128-token output run to check how TPOT changes with output length.
- Run the same sweep on a second T4 session to check repeatability across
  hosts.
